1. EXECUTIVE SUMMARY & PURPOSE
--------------------------------------------------------------------------------
The Backend REST API Load Testing Framework in Playwright is designed to stress-test
real backend REST microservices hosted on Azure App Service:
Target Host: https://dev-ux-linux-ezabgbfbfxh3gggs.southindia-01.azurewebsites.net

WHY DIRECT REST API LOAD TESTING IS CRITICAL:
1. Bypassing Static Frontend CDN:
   Navigating frontend routes on azurestaticapps.net serves static HTML/JS assets
   from a CDN edge cache (~7ms response) and DOES NOT generate CPU/RAM load on 
   the backend server.
2. Generating True Azure App Service Load:
   Direct HTTP POST/GET spikes against southindia-01.azurewebsites.net force Azure's
   Linux App Service host, C# ASP.NET Core controllers, and SQL/MongoDB databases 
   to process heavy concurrent transactions, generating true server-side latency
   and resource performance metrics.

4. ASYNC / AWAIT & PROMISE.ALL() HIGH-CONCURRENCY ARCHITECTURE
--------------------------------------------------------------------------------

WHY ASYNC / AWAIT IS USED:
JavaScript is single-threaded and event-driven. Using "async" functions and "await"
allows Playwright to perform asynchronous, non-blocking I/O network calls.
Instead of opening 500 heavy physical browser tabs (which would consume 50GB RAM 
and crash your computer), async functions allow Node.js to manage 500 concurrent 
HTTP socket connections in a lightweight event loop using less than 50MB RAM.

HOW PROMISE.ALL() GENERATES PARALLEL SPIKES AT THE EXACT SAME MILLISECOND:
Promise.all() accepts an array of asynchronous HTTP fetch promises. Rather than 
executing requests sequentially one-by-one (Request 1 -> Wait -> Request 2), 
Promise.all() initializes and dispatches ALL N (500, 700, 1000) HTTP requests 
simultaneously across the network interface at the EXACT SAME MILLISECOND:

Code Pattern:
--------------------------------------------------------------------------------
const apiHitResults = await Promise.all(
    Array.from({ length: hitCount }).map(async (_, idx) => {
        const startTime = Date.now();
        const response = await context.request.fetch(targetApi.url, {
            method: targetApi.method,
            headers: apiRequestHeaders, // Carries Bearer Authorization Token
            ...(targetApi.postData ? { data: targetApi.postData } : {}),
            timeout: 45000
        });
        const responseTimeMs = Date.now() - startTime;
        return { status: response.status(), responseTimeMs };
    })
);
--------------------------------------------------------------------------------

IMPACT ON AZURE APP SERVICE:
For the backend server on southindia-01.azurewebsites.net, receiving 500 requests
via Promise.all() is 100% IDENTICAL to receiving requests from 500 separate browser 
tabs or 500 real users clicking the button at the exact same millisecond. 
It forces Azure's thread pool and SQL database connections to handle peak spike load.


5. COMPLETE 2-PHASE ARCHITECTURE & STEP-BY-STEP PROCESS
--------------------------------------------------------------------------------

PHASE 1: STRICT UI LOGIN & DYNAMIC NETWORK INTERCEPTION
-------------------------------------------------------
Step 1: Headless Browser Launch
        Playwright launches a headless Chromium browser instance with clean HTTP headers.

Step 2: Automated UI Login
        Navigates to the frontend login route (/login), enters valid credentials
        (superadminmartinrea1@martinrea.com / Dell@1234), and submits the login form.

Step 3: Identity Validation & Token Extraction
        The backend validates credentials via /Login/LoginGateWayValidateUserByID and
        issues an official JWT Bearer Token (Bearer eyJhbGciOi...).
        Playwright automatically parses and extracts this token directly from the
        HTTP response JSON payload and browser storage (localStorage / sessionStorage).

Step 4: Pre-Login Cache Flushing
        Clears pre-login unauthenticated requests to ensure that ONLY post-login 
        authenticated routes carrying valid session tokens and JSON request bodies
        (postData) are recorded for load testing.

Step 5: Module Page Navigation & Endpoint Interception
        Programmatically navigates through target module pages (e.g. Master pages,
        Admin pages, Dashboard, Process Monitor, etc.).
        As the Angular frontend calls backend REST APIs, Playwright's network 
        interceptor captures:
        - Full Target API URL (e.g., https://.../api/Group/GetScreenDetailsForLayout)
        - HTTP Method (POST / GET)
        - Active Request Headers
        - Exact JSON Request Body Payload (postData)


PHASE 2: HIGH-CONCURRENCY PARALLEL LOAD SPIKES (Promise.all)
------------------------------------------------------------
Step 6: Header Sanitization & Injection
        Before firing load hits, Playwright strips browser-specific headers
        (Host, Content-Length, Cookie, :authority) so the HTTP client auto-populates
        the correct target host headers. It then injects:
        - Authorization: Bearer <JWT Token>
        - Content-Type: application/json

Step 7: Simultaneous Spike Load Execution
        For each intercepted backend API endpoint, Playwright uses Promise.all() to fire
        N (e.g., 50, 100, 500, 700, 1000) simultaneous HTTP requests at the EXACT 
        SAME MILLISECOND directly to Azure App Service.

Step 8: Metric Recording & Log Persistence
        Measures response latency (ms), status codes (200 OK), and payload size (bytes).
        If any request times out (>45s) or fails, Playwright writes a clean 1-line 
        log to the logs/ directory.

9. INFRASTRUCTURE & CAPACITY RECOMMENDATIONS
--------------------------------------------------------------------------------
1. Single Instance Capacity:
   A single Azure App Service Linux instance (southindia-01.azurewebsites.net)
   comfortably handles up to ~350-400 concurrent simultaneous API hits per batch 
   with sub-2-second response times.

2. Production Auto-Scaling:
   To support 1,000+ simultaneous peak users with sub-2-second latency in production,
   configure Azure App Service Auto-Scaling (2 to 4 instance scale-out) and 
   increase database connection pool limits.
